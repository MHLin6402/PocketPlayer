# AI Agent Guide

This file is for an AI coding assistant (Claude, or similar) helping someone
extend PocketPlayer - written so a non-programmer can point their AI
assistant at this file and say "read this, then help me add X." It collects
the openFPGA/Analogue Pocket platform gotchas this project actually hit
during development, so you don't have to rediscover them the hard way.

For the story behind *why* any of this is true - the actual bug reports,
Fitter error messages, and dead ends - see
[DEVELOPMENT_HISTORY.md](DEVELOPMENT_HISTORY.md) (44 numbered sections, in
order). This file is the condensed, "here's what you need to know before
touching the code" version.

## Before you start

- The user builds in Quartus and tests on real Analogue Pocket hardware -
  you (the AI) cannot compile, flash, or run this core directly. After any
  HDL change, the user needs to recompile in Quartus, copy `dist/` to the
  SD card, and test on the device. Structure your help accordingly: make
  the change, explain exactly what to test, and be ready to iterate from
  their report (ideally including the debug log from
  `/System/Logs/` on the SD card, which records the boot sequence and any
  APF-level errors).
- Use `py` (not `python`/`python3`) if you're on the same kind of Windows
  setup this project was developed on - check what's actually available in
  the current environment rather than assuming.
- Terminal commands you hand the user must be single-line and pasteable
  as-is into PowerShell - no backtick line-continuations (they silently
  break when pasted).

## Repo layout

- `open-fpga-core-template-da3a021/` - the actual FPGA core. `src/fpga/`
  holds the Quartus project (`ap_core.qpf`/`.qsf`) and `core/core_top.v`
  (the top-level design - most of the interesting logic lives here) plus
  its supporting modules (`audio_streamer.sv`, `playlist_ram.sv`,
  `track_thumb_ram.sv`, `psram_audio_buffer.sv`, `psram.sv`, `font_rom.v`).
  `core.json`/`data.json`/`interact.json`/`video.json` here are the
  "source of truth" template copies - `dist/`'s copies must be kept in
  sync by hand when either changes.
- `dist/` - the deployable folder: copy its contents to the root of an SD
  card to install/update the core. `dist/Cores/mhlin.PocketPlayer/` (must
  be named exactly this - see the folder-naming rule below) holds the
  compiled bitstream + JSON configs; `dist/Platforms/` holds the menu
  category/banner entry; `dist/Assets/pocketplayer/common/` (not shipped
  in this repo - generated by the user's own `tools/convert_audio.py` run)
  holds the actual audio/playlist/thumbnail data read at runtime.
- `tools/` - Python scripts that generate everything in
  `Assets/pocketplayer/common/` from the user's own music files, plus
  `make_rbf_r.py` (bitstream post-processing) and `make_icon.py`/
  `make_default_thumb.py` (regenerate the app icon / fallback album art).
- `docs/DEVELOPMENT_HISTORY.md` - the full build log, described above.

## Deploy flow (any time HDL changes)

1. Quartus: open `open-fpga-core-template-da3a021/src/fpga/ap_core.qpf`,
   compile.
2. Convert the bitstream (Quartus produces `.rbf`, the Pocket needs
   bit-reversed `.rbf_r`):
   `py tools/make_rbf_r.py open-fpga-core-template-da3a021/src/fpga/output_files/ap_core.rbf dist/Cores/mhlin.PocketPlayer/bitstream.rbf_r`
3. Copy `dist/` to the SD card's root (merging with its existing contents,
   not replacing the whole card).

If only Python-tool output or JSON config changed (no HDL edits), skip
straight to step 3 - no recompile needed.

## Platform gotchas (openFPGA / Analogue Pocket APF)

- **SD card folder naming is exact-match and fails SILENTLY.** The SD
  folder must be named exactly `<core.json metadata.author>.<core.json
  metadata.shortname>` (currently `mhlin.PocketPlayer`). If it doesn't
  match, the Pocket can't find the core's files, the load aborts silently
  (the debug log just stops right after "Opening
  /Cores/<author>.<shortname>/core.json", no error message), and the FPGA
  stays on whatever core ran previously. Whenever you change `shortname`
  in `core.json`, the SD folder name must change to match, everywhere
  (including any old copy still sitting on a test SD card - it needs
  deleting, not just superseding, or you can end up with two entries).
- **`platform_id` must be unique AND <= 15 characters.** `core.json`'s
  `platform_ids` selects `/Platforms/<id>.json` + `_images/<id>.bin` +
  `Assets/<id>/common/`. Two cores sharing a `platform_id` (e.g. the stock
  template default `ex_platform`) merge into one confusing "Change Core"
  menu entry. Separately, anything over ~15 characters gets silently
  truncated when the Pocket OS builds the `Assets/<platform_id>/common/`
  path (asset loads silently fail) and can overrun a buffer in openFPGA's
  own platform-list cache builder, causing a screen-flash crash loop
  recoverable only by holding Power. This project hit both failure modes
  for real during development (see DEVELOPMENT_HISTORY.md's early
  sections) - if you ever change `platform_id`, keep it short and unique,
  and update `dist/Platforms/<id>.json` + `_images/<id>.bin` + the
  `Assets/` folder name to match.
- **The SD-card asset-loading (`target_dataslot_*`) protocol has strict
  rules**, all implemented correctly in `audio_streamer.sv`/
  `playlist_ram.sv` - if you add a new data slot, follow the same pattern:
  1. `target_dataslot_length` must never exceed the file's `size_exact` in
     `data.json`, or the Pocket returns "Error servicing operation. Did
     you read too far?" and the request hangs forever. Pad any file to
     exactly the length something will request from it.
  2. The read handshake is exactly 4 states: pulse `read=1` for ONE clock,
     wait for `!done`, wait for `done`, done. Holding `read=1` continuously
     or collapsing to 3 states prevents `target_dataslot_done` from ever
     completing. Default `target_dataslot_read <= 1'b0` at the top of the
     always block so it's a clean 1-cycle pulse.
  3. A data slot with an `"address"` field gets its ENTIRE file
     auto-loaded at boot regardless of `"required"`. For any slot your
     core reads on-demand at runtime instead (like the audio banks here),
     add `"deferload": true` or you'll pay a real boot-time cost loading
     bytes the core never actually uses from that copy.
  4. `target_dataslot_done` is ONE signal shared by every module wired
     into the arbitration mux - not tagged per request. Only ONE module
     may have a request outstanding at a time, system-wide. If you need a
     new module to also fetch data slots, do NOT just OR its
     `target_dataslot_read` into the mux alongside existing ones unless
     you're certain their in-flight windows can never overlap - instead,
     fold new fetch work into an EXISTING single-requester module as a
     lowest-priority filler task (see `audio_streamer.sv`'s own layered
     priority chain - audio chunks, then album art, then Library row
     icons - as the reference pattern for this).
- **On-chip memory array inference has three independent traps**, and
  Quartus fails SILENTLY (falls back to expensive registers/LUTs, not an
  error) if you miss any one of them. If you ever grow an array
  (`playlist_ram.sv`'s `pram[]` is the reference example, MAX_TRACKS 8 ->
  32 -> 512 across this project's history) and the Fitter suddenly can't
  fit the design, check all three:
  1. **Read side**: each read port must touch exactly ONE address per
     cycle. Reconstructing a wide record from several different word
     addresses in the same cycle (`arr[{idx,5'd1}]`, `arr[{idx,5'd2}]`...)
     is not a block-RAM read pattern - store ONE WIDE ROW per record
     instead, then bit-slice the single fetched value (free) rather than
     re-reading the array per field.
  2. **Write side**: writing into a variable-offset slice of an array
     element (`arr[idx][var_offset +: W] <= data`, where `var_offset` is a
     signal) is ALSO not a block-RAM write pattern. Stage incoming data in
     a plain (non-array) register first, then commit the whole row in ONE
     full-width write.
  3. **Registered reads**: `wire = arr[idx]` (combinational) NEVER infers
     block RAM on Cyclone V - M10K only has synchronous read ports. Use
     `always_ff @(posedge clk) row <= arr[idx];` instead. This adds 1
     cycle of latency; check whether the new address is predictable one
     cycle ahead (a free-running counter, or a register's own next-value
     logic) so you can feed the memory that predicted address early
     instead of retiming every downstream consumer.
  Diagnostic tell: if "Total block memory bits" in the Fitter report
  doesn't move AT ALL between two attempts, the array was never landing in
  block RAM in either of them - don't conclude a fix worked from "the
  Fitter error message changed" alone, check the actual bit count.
- **Display Mode filters** (`video.json`'s `display_modes` array, separate
  from any in-core setting) - "Normal" is always auto-prepended, array
  order is menu order. Valid IDs are documented in Analogue's own
  core-definition-files docs; this project's current list (CRT Trinitron,
  several Game Boy/GBA-family LCD styles, a couple of retro/novelty
  filters) is in `dist/Cores/mhlin.PocketPlayer/video.json` and
  `open-fpga-core-template-da3a021/video.json` if you want to add more.
- **`interact.json` "list" variables have an undocumented size limit.**
  This project once tried a 356-option Settings-menu list (one entry per
  track) and it made the core fail to boot entirely ("Load error in
  'interact', General error" - the debug log just stops after "Opening
  .../interact.json"). The file was valid JSON; it was simply too big/had
  too many options for something that had only ever been tested with a
  couple dozen entries before. Keep `interact.json` lists small (tens of
  entries, not hundreds) - if you need a large browsable list, do it
  in-core (like PocketPlayer's own Library tab, which reads D-pad input
  directly in `core_top.v` and has nothing to do with `interact.json`) not
  through the Settings menu.
- **A 32-bit `target_dataslot_slotoffset` hard-caps any single data slot
  at 4GB.** `audio_streamer.sv` addresses an audio chunk as
  `{chunk_idx[12:0], 19'b0}` (13 bits × a 512KB chunk size exactly fills
  32 bits) - so no single data slot can ever address more than 8,192
  chunks of content, full stop, regardless of chunk size chosen. This
  project hit it for real once the library grew past ~110 tracks of
  uncompressed audio and fixed it by splitting the audio into multiple
  "Audio Bank N" data slots (see `playlist_ram.sv`'s `audio_bank` field
  and `audio_streamer.sv`'s `AUDIO_SLOT_ID_BASE` for the pattern) rather
  than one giant file. If you're adding any large on-demand-streamed asset
  of your own, do the arithmetic up front: `4GB / your_chunk_size` is your
  real per-slot ceiling.

## PocketPlayer-specific architecture notes

- `core_top.v` is organized around a 2-bit `cur_tab` (NowPlaying=0,
  Library=2) and (within NowPlaying) a 2-bit `effect_mode` (Still
  Thumbnail / Spinning Vinyl / Full Art). Most rendering wires are gated
  by both, e.g. `(cur_tab_vid == 2'd0) && (effect_mode_vid != EFFECT_FULL_ART)`.
  If you add a new visual element, follow this same gating pattern rather
  than inventing a new one.
- Cross-clock-domain signals (buttons/settings from `clk_74a` needed by
  the `clk_core_12288` video renderer) are synced with `synch_3` instances
  near the bottom of `core_top.v` - grep for `synch_3` to see the existing
  ones and match their pattern (width parameter must match the signal's
  actual bit width, e.g. `synch_3 #(.WIDTH(2))` for a 2-bit signal).
- Button input uses `cont1_key[N]` bits: `[0]`=Up, `[1]`=Down, `[2]`=Left,
  `[3]`=Right, `[4]`=A, `[6]`=X, `[7]`=Y, `[8]`=L, `[9]`=R, `[14]`=Select,
  `[15]`=Start (`[5]`/B is currently unused). Every button handler follows
  a rising-edge-detect pattern: a `btn_*_r` register holds last cycle's
  raw state, and the actual action fires on `cont1_key[N] && !btn_*_r`.
  The button lock (`input_locked` wire) and screensaver
  (`screensaver_vid`) gate almost everything else - if you add a new
  button action, gate it with `!input_locked` too, following the existing
  examples, or it'll keep responding while the player is supposedly locked.
- Playback state (`playlist_ram.sv`) uses a "one wide row per track"
  layout specifically to satisfy the memory-inference rules above - if you
  add a new per-track field, extend the record format (there's reserved
  space) rather than adding a second array.
